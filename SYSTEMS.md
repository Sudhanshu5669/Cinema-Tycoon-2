| 6  | Tile renderer + 3/4 perspective wall faces | done | `src/game/tilemap/`. Built with an **elevation model** from the start, per user direction ("versatile enough to have levels"): a map carries a `height` grid (integer terrain elevation, 0 = street) plus ordered `layers` with roles `ground`/`flat`/`object`/`overhead`, and `buildings`/`platforms` sugar the renderer expands. A cell's top surface is drawn `e * STEP` px up (`STEP` = one tile, in `projection.js`, a renderer knob not a locked art constant); the vertical drop to lower ground in front is drawn as an **oblique face projecting straight down** — no horizontal skew, so it stays compatible with a 4-facing character. **Buildings are a roof cap + a composed storeyed face** (cornice / wall / ground-floor material / plinth, `faceRowPlan`) with windows and a door placed in face space, plus a cast shadow on the pavement — this is what un-flattens the old straight-on-facade look. Everything static is baked into offscreen **canvas textures** (`atlas.js` `bake`), not RenderTextures: painting a 1920px ground plane cell-by-cell into a RenderTexture stalls for seconds on GPU readback, a 2D canvas does it in ms and the result is one static image with no per-frame cost. Depth sort is by world-Y of ground contact: the player's feet (`player.js` sets `sprite.depth`) vs each structure's front-wall line, so the player is behind a building unless their feet are south of it; roof and face share that depth. `heightAt`/`solidAt` are exposed for collision (#7), which now builds on them. **Elevated surfaces catch shadows too**: a shadow's hull is computed in ground coordinates, so it paints straight onto the flat street, but a roof cap or a platform top is drawn shifted (and, for a foreshortened roof, squashed) relative to that same footprint — a hull painted only on the ground can never visually land on one, since the elevated surface's own image, at a much higher depth, just sits in front of it. Every roof cap and platform top gets its own small baked layer: any *other* caster's hull is clipped to that surface's footprint (Sutherland-Hodgman against the footprint rect, `clipToRect` in `shadows.js`) then carried through the same footprint -> screen transform the surface's own top image uses, so a tall neighbour's shadow correctly darkens a shorter roof or a nearby raised platform; a surface excludes its own caster index, or it would always contain its own unshifted footprint and paint itself solid black every frame. A clip along two footprints' shared edge degrades to a zero-area sliver rather than a real overlap, so the hit test is gated on polygon area (shoelace), not just point count — a raw `length >= 3` check flagged every contiguous building pair as shadowed at every hour, noon included. Art started as the SYSTEMS #0 placeholder tiles (`art/flat/tiles.mjs`); a later detail/variety pass (per user request, "more surface detail/variety") added a window sill (reusing the cornice's own lip/shadow tones rather than a new ledge language), denser irregular wall speckle, a tar-and-gravel roof speckle in place of a few sparse patches, sparing darker-brick flecks alongside the existing lighter one for brick colour variety, and a `paveStain` tile (an old stain, sparingly placed via `city.json` cells the same way `paveCrack` already was) — all within the same flat/no-outline/two-tones-per-material discipline the player sprite set, no new palette entries needed except where noted. The door tile, on inspection, already had this level of detail (an inset glass pane, a handle, a raised panel, a threshold matching the plinth) and was left alone. **Second follow-up from user review**, "windows and doors are too thin... Researched properly before building rather than guessing at the risk that sank the earlier character-sprite attempt (GAME_SPEC's rejected direction #1, smooth normal-based falloff reading as "glassy, moulded plastic"): a [Phaser normal-map atlas example](https://phaser.io/examples/v3.55.0/loader/texture-atlas-multi/view/load-multi-texture-atlas-with-normal-maps) confirms the loader takes a `normalMap` URL directly; a survey of pixel-art normal-map techniques ([arXiv:2212.09692](https://arxiv.org/pdf/2212.09692)) confirms the usual hard part — a finished raster image can't say what a colour's height was meant to be — genuinely doesn't apply here, because these tiles are never a finished raster first: they're ASCII grids where every character already has one fixed, intentional meaning. `art/flat/palette.mjs`'s new `TILE_HEIGHT` says what that meaning's relative height is (a cornice lip is raised, its mortar groove recessed, glass sits behind its frame), once, and `tools/normals.mjs` derives a normal map from any tile's own grid + that table via a central-difference slope estimate — no separate art to author, and the failure mode that sank the sprite attempt is designed around directly: small height deltas, sharp 1-2px transitions rather than smooth gradients, since a crisp step reads as an edge, a gentle continuous ramp is what read as plastic. Per-tile `RELIEF_STRENGTH` (`build-tiles-sheet.mjs`) scales how strongly that shared height table tilts each tile's own normal, so a belt course can be a subtler ledge than the main roof cornice despite reusing the exact same `l`/`L` height values; most tiles (WALL's speckle, ROOF's gravel grain, PAVE/ROAD/GRASS) are left at strength 0 -- stochastic texture, not a structural edge, so they stay exactly as flat as before this system. The harder half of this wasn't the normal-map math, it was that the renderer bakes many tiles into one flat composite canvas per structure (a building's whole face, its roof, the ground -- see this row's own "Everything static is baked" note) for performance, and a plain 2D `drawImage` bake has no way to also carry a normal map through: the result would be a brand-new texture Phaser has never seen, silently falling back to a flat default normal no matter how much relief the source tiles carried. Fixed in `atlas.js`'s `bake()`: every `draw` call now paints twice in lockstep, once against the diffuse atlas image as before and once against its normal map into a second plain canvas, attached to the bake's own texture afterward via `Texture#setDataSource` -- the same mechanism a loaded atlas-with-normal-map uses internally, just applied at runtime to a canvas nothing has loaded from disk. The 32px jump had been reasoned from a false premise: FEATURES don't actually answer to the 16px tile grid at all (only TILES do -- they're the ones repeat-tiled by atlas.js's `fill()`; a window or door is placed once, at one pixel offset, via `tile()`, and can be whatever width its own art calls for). `build-tiles-sheet.mjs`/`build-tiles.mjs`'s width-is-a-multiple-of-16 validation was only ever checking `TILES`, tightened to stop applying it to `FEATURES` too. Atlas built by `node tools/build-tiles-sheet.mjs` -> `public/assets/tiles.{png,json}` (added to `npm run build:art`); `tools/build-tiles.mjs` is the separate static review sheet. Dev map is `public/assets/city.json` (a row of buildings, a kerbed road, one raised grass platform at elevation 2, streetlamps, one object + one overhead cell) since SYSTEMS #9 replaced the original hardcoded `devmap.js`. **Cast-shadow layer** (`shadows.js` + `sun.js`): every raised caster (building or platform) drops a shadow on the street whose **length scales with its silhouette height** and whose **length, direction and opacity track an hour-of-day**. `sun.js` is a deliberately cheated sun — a physical one spends midday south of the street throwing shadows north, away from the camera and behind the buildings, so this one is kept low and behind the viewer all day: shadows always rake south onto the visible pavement, swinging south-west in the morning to near-straight-down and short at noon to south-east (and long) in the evening, and fading out between dusk and dawn. Evening agrees with the west-lit flat tiles; the morning half-hour disagrees, which is a job for the #8 light pass. Each shadow is the convex hull of the caster's ground footprint swept along the sun offset; all of them are painted solid black into one throttled offscreen canvas (~0.05h buckets) and shown as a single Image whose alpha is the hour's shadow opacity — baking a flat mask and fading it once is what stops contiguous buildings' shadows stacking into double-dark seams. The hour is just a settable value here (`__dev.setTime` / `__dev.autoTime`, HUD `time` line, `DevScene.START_HOUR`) — plus dev-only hotkeys (`DevScene.bindDevHotkeys`, raw `keydown`, gated on `import.meta.env.DEV` the same as `__dev` itself) for testing without a console open: `1`-`6` jump to dawn/morning/noon/afternoon/dusk/night, `[`/`]` step an hour, `T` toggles auto-advance; the HUD prints the binding so it doesn't have to be remembered; the real day/night clock is #16 and the coloured day/evening overlay is #8. Deliberately its own small canvas (`ShadowLayer.updatePlayer`, `PLAYER_SHADOW_REACH` around the player), not folded into the world-sized static bake above -- the player moves every frame, buildings/platforms/streetlamps never do, and redoing that whole unmoving bake on every step would be pure waste. Reuses the existing sprite-silhouette shear technique unchanged (the player is exactly the same "thin, irregular caster" case a streetlamp already was) for the sun shadow; a *point*-light shadow is the same shear math with a different (dx,dy) -- normalized direction away from the light, scaled by proximity (`PLIGHT_MIN_LEN`..`PLIGHT_MAX_LEN`, both length and darkness fading together as the player nears a light's own edge) -- since unlike the sun, a light has a position, so the direction is different every time the player moves relative to it. `LightingLayer#shadowSources` (#8) reports the nearest lit lights actually close enough to be lighting the player at all (capped at 2, so more than one nearby lamp can throw its own separate shadow, same as real point-source light). Bucketed on player position + frame + hour + light state so an idle player under a still sky redraws only on its own idle-blink frame change. Verified in real Chromium: `node tools/smoke.mjs` -- the player's shadow reads along the sun's own direction and not the opposite way, and away from a nearby streetlamp rather than toward it (sampling a small spread of distances along each direction and taking the max, since the character's own silhouette has real gaps -- the legs -- that a single exact-pixel sample can land inside of and misread as unlit); the existing walk-speed real-time check (the same canary that caught the `maxLights` and Bloom regressions earlier) stayed green across repeated runs, confirming the per-frame small-canvas redraw is cheap enough. **Caught by the user against a screenshot, a real bug in the system, not the test that first hid it**: every light point's `x, y` is its *glow* position (a streetlamp's bulb, well above its map placement near the top of the pole), and the player-shadow direction was computed straight from that -- using an elevated position as if it were where the light stood on the ground put the "away from the light" direction visibly wrong the moment the player stood right next to the post. Fixed by giving each light point a separate ground anchor (`gx, gy` in `renderer.js` -- a streetlamp's own base; a window or the marquee's is straight down the wall to the pavement, `frontY`) that `shadowSources` now returns for direction, while `dist`/`radius` stay against the *glow* position (what the shader's own falloff is centred on, i.e. "is this light actually reaching the player" is a different question from "which way is away from it"). Fixing this surfaced a second, sharper bug the first screenshot's exact geometry happened to sit right on top of: the sprite-silhouette shear's y-scale is `-dy/H`, singular at `dy = 0` -- entirely ordinary once a light has its own position instead of one shared sun angle (a player walking along a row of streetlamps is level with one every time they cross it) -- which silently erased the shadow rather than merely mis-aiming it. The first fix for that also tried flooring the shadow's own southward component, copying the sun's own "always rake south" cheat (`sun.js`'s header explains why that's a valid cheat *for the sun* -- it has no real position to violate). That was itself wrong, and the user caught it in the very next screenshot: a streetlamp does have a real, fixed position, so forcing every shadow toward south points it *toward* a light that happens to be south of the player, backwards rather than merely stylised. Reverted -- the singularity fix stays (nudging `dy` a hair off *exactly* zero, sign preserved, in `_paintSpriteShadow` alone), with no directional bias layered on top of it. Verified in real Chromium, standing on both sides of the same lamp: the shadow now reads away from it whether the player is north or south. **Third follow-up, a real architectural redesign this time**: even fixed, the same spot could still show visibly different shadows a few px apart, because `shadowSources` picked the nearest 2 lights by rank -- crossing the exact point where a third light overtakes the second reassigns the set outright, and every reassignment is a visible jump, indistinguishable from "hardcoded" to someone watching it happen. Researched rather than patched again: [Godot's own `Light2D`](https://docs.godotengine.org/en/stable/classes/class_light2d.html) is just colour + an intensity multiplier ("energy") + a falloff radius, blended additively, no concept of "which light wins"; real multi-source lighting physics is unambiguous that every source illuminates (and shadows) independently, its own strength set only by its own falloff, never by competing against other sources. **`src/game/light.js`, new**: a `Light` class -- position, an optional separate ground anchor, radius, colour, intensity, a `kind` label, a `castsShadow` flag -- is now the one object every light in the game is built from (a window, the marquee, a streetlamp, or anything added later -- a torch, a lantern the player carries -- by construction options, never a new special case). `Light#illuminationAt(px, py)` is the single authoritative "how lit is this point" answer, using the *same* `1 - d²/r²` falloff Phaser's own shader renders, so a shadow's strength always tracks what the eye actually sees glowing; `Light#directionFrom` is the shadow-direction half, off the ground anchor. `LightingLayer` (`lighting.js`) now holds an array of `Light`s (one Phaser Light2D instance kept in sync with each, for the glow) instead of the old parallel `points[]`/`lights[]` arrays. `shadowSources` dropped the ranked cutoff entirely: it returns *every* light whose illumination at the point is above a negligible floor (no cap needed -- only lights whose radius geometrically reaches the point ever qualify, so the list stays small on its own), sorted strongest-first as a convenience only, nothing excluded by that order. `shadows.js`'s `updatePlayer` draws one shadow per source, its length and darkness both driven directly by that light's own `illuminationAt` -- no ranking left anywhere to reassign. Verified in real Chromium: walking the player at 12px steps across two evenly-spaced streetlamps (through the region where the qualifying set genuinely changes, 2 lit -> 3 -> 2 again), the dominant light's own strength changes by at most ~0.06 between steps -- continuous, not a pop -- confirming the set changing underneath it is invisible, exactly the intended effect of weighting by illumination instead of rank. **Sixth follow-up, per user request** ("make the whole city look and feel dense and detailed... make different types of tiles for the entry, make it look like a cheap cinema from Los Angeles"): five new tiles, all reusing existing palette tones except three small additions -- poster paper (`j`/`J`, a deliberately-warm exception following BRICK's own precedent), muted street-clutter metal (`Z`/`Q`), and one terrazzo ground tone (`O`). `BOX_OFFICE` (24x32, a FEATURE like WINDOW) is a walk-up ticket booth -- uniform dark glass under a small hood-shadow, a red placard band reusing the marquee's own accent rather than adding a second one, a brass ticket-slot pixel on its base. `POSTER_CASE` (16x32) is a glass-fronted display case, one flanking each side of the door, holding an abstracted image block (no font tile exists to print a real title) on faded paper with a single torn-corner pixel for the cheap, well-worn look asked for.
